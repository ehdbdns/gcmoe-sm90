### IR 口径（本表用新口径）

旧口径把 1000 步 × 40 层**先全部求和再算** `max_rank/mean_rank`，求和让各 rank 的偏离
互相抵消，而 `max/mean` 不是线性泛函 —— **逐步的不均衡无法从窗口求和里恢复**。

新口径由 dispatch kernel 在测量窗口内按 `(layer, step)` 直接记录，然后：

```
每个 (step, layer) 对:  IR = max_r tok[r] / mean_r tok[r]      <- 8 个 rank
对 40000 个对取平均     -> ir_step_layer_mean
```

计算时同时得到 **Poisson 零假设基线** `null = 1 + 1.42/sqrt(m)`（m = 每 rank
每层每步的 token 数）：即使放置完全均衡，`max/mean` 也会大于 1，所以
`excess = IR - null` 才是放置真正贡献的部分。这两个量仍写进每个 run 的
json（`ir_step.ir_poisson_null_mean` / `ir_excess_over_null`），下表只列 IR 本身。

**★ 为什么「M块数平均」与「激活专家数平均」几乎相等**：本 workload 下每个
**激活**槽的 token 数都小于一个 `block_m`（BS=256 时全 rank 平均
`1536/384 = 4` token/槽，`block_m = 64`），所以 `ceil(tok/block_m)` 恒为 1
⇒ 一个激活槽恰好产生一个 M 块。这不是测量错误，是 `per_slot ≪ block_m` 的直接结果；
它也解释了为什么 `M块数` 与 `激活专家数` 两列可以互相校验。

**但「M块 IR」与「IR」不等价**，两者衡量不同层面：四档的 `random` 臂
token IR 都比原生差（例如 BS=32: 1.5357 vs 1.4769）而 M块 IR 都更好
（1.2880 vs 1.3133），原因是它把槽数从 48 提到 56（+17%），槽多了每槽 token 更少，
取整后全是 1 块，M 块维度的不均衡被稀释。两列都要看。

### 关键结论

1. **SM-reuse 随 batch 增大单调占优**：BS=32 与原生打平（+0.05%），
   BS=64 **−2.30%**、BS=128 **−3.97%**、BS=256 **−6.37%**（相对同档原生）。
   BS=32 是个位数百分点的边界情形：此时每槽平均不到 1 个 token，
   副本的固定开销（每 rank 多 8 槽）与均衡收益刚好抵消。
   BS=256 上 `rr` 的 ms 与 SM-reuse 持平（69.40 vs 69.47），但 SM-reuse 的
   token IR 好得多（1.2705 vs 1.3314），且 M块 IR 也更好。

2. **random（随机放置）在四档里都最慢**（+9.94% / +6.52% / +6.39% / +4.06%），新口径 IR 也最高（1.4916–1.5357，比原生高 4–6%）。  ⇒ **随机打散是有害的**：它把热点专家随机聚到同一 rank 上。这也说明「放置质量」比「是否复制」更重要。

3. **EPLB 放置（rr）随 batch 增大从劣势转为优势**：BS32 +9.38% / BS64 +3.32% / BS128 -0.33% / BS256 -6.47%。副本开销被摊薄后，均衡收益开始占主导。

4. **同样的 8 副本/rank，ECO 的 IR 在四档里都优于 host 轮询（rr）**：
   BS32 1.3833 vs 1.4439、BS64 1.3586 vs 1.3780、BS128 1.3014 vs 1.3479、
   BS256 **1.2451 vs 1.3314**（越低越好）。速度上 BS≤128 也是 ECO 更快
   （+0.81% vs +9.38% / −0.99% vs +3.32% / −1.66% vs −0.33%）；
   只有 BS=256 时 rr 略快（−6.47% vs −5.34%），但它的 IR 差 6.9%。
   ⇒ 内核 plan 把副本切成不等长 quota，**用均衡换到的东西更多**；
   在 BS=256 这种算力紧张的场景里，rr 靠"少搬一点"赢回 1.1% 的墙钟，
   代价是 rank 间不均衡回升。

5. **「M块数平均」与「激活专家数平均」两列几乎完全相等**（20 个 run 逐位核对）：

   | BS | 两列之差（全部 5 臂） |
   |---:|---|
   | 32 | **0.000**（逐位相同）|
   | 64 | **0.000**（逐位相同）|
   | 128 | 0.002 – 0.059 |
   | 256 | 0.39 – 0.85（< 0.3%）|

   原因：绝大多数激活槽的 token 数小于一个 `block_m`，`ceil(tok/block_m)` 恒为 1；
   到 BS=128 才有个别槽刚超过一个 `block_m`（例如 `block_m=32` 时 33 个 token），
   BS=256（`block_m=64`）时这种槽略多，两列才开始有微小差别。
   ⇒ 这两列可以互相校验，但**不是同一个指标**：`mb` 会在 `block_m` 边界上跳，
   `ae` 不会。

6. **「M块 IR」与「IR」方向并不总一致**：四档的 `random` 臂 token IR 都比原生差，
   而 M块 IR 都比原生**好**（BS=256: 1.1048 vs 1.1114）。原因是副本把槽数从 48
   提到 56，每槽 token 更少、取整后基本都落在 1 块，M 块维度的不均衡被稀释。
   同理 BS=128 的 `rr` 与 `eco`：token IR 是 rr 更差（1.3479 vs 1.3014），
   但 M 块数 rr 明显更多（280.5 vs 234.6）。**两列衡量不同层面，必须都看。**

### 稳健性：20 个实验的生产者/消费者时间线

⚠️ 本轮全部 20 个实验**只跑数据文件 `_1`**，并用 1000 步 warmup + 1000 步测量
（上一轮曾用两个文件各跑一遍 BS=32 做健壮性对照，结论是五臂排序在两个独立切片上
完全一致：`random` 的速度差 0.05%、IR 差 0.65%）。本轮把预算换成
「4 档 batch × 5 臂 × 更长窗口 + 每臂一张时间线图」，因为 batch 维度上的趋势
比第二个数据切片更有信息量。

时间线的数据来自 **测量窗口内某一层**（rank 0），逐事件记录：

* **上排 = 生产者**：每 pull 完一个槽，在该时刻累加该槽发布的 GEMM task 数；
  蓝点线 = **该层全部槽 pull 完成的时刻**（dispatch 在此刻释放 6 个 SM）
* **下排 = 消费者**：每**开始**一个 GEMM task 累加 1，橙色 = role 2，
  红色 = role 6（SM-reuse 的帮助者）；灰色细虚线 = 两者合计**完成**的 task；
  红虚线 = **role 6 开始第一个 task 的时刻**，红色阴影 = role 6 参与的时间区间；
  灰粗虚线（右轴）= 未完成积压
* **单位是 task（= 一个 `(slot, N-tile)` 块，一条 `type 6/7` 记录）**，即 kernel
  真正调度和领取的单位。消费者线因此从 11–20 µs 就起来 —— 一个槽刚 pull 完，
  它的 task 就立刻可以领，GEMM 与剩下的 pull 重叠；若改用"M 块全部 N-tile 都
  完成"作单位，第一点会被推迟到 389 µs，把整个重叠段藏掉。

## ★ SM-reuse：把 dispatch 腾出的 6 个 SM 交给 compute

### 一句话

**不是**「停掉 dispatch kernel 再新建一个 compute kernel」，而是**同一个 CUDA graph 里
多挂一个 kernel 节点（role 6）**：它和 dispatch 共用 dispatch 的 green context，
graph 依赖保证它在 dispatch 返回之后才被调度，dispatch 空出来的 6 个 SM 就自然被它占住，
一直算到本层结束。

### 实现细节（`runtime/sm90_gc_moe.py` + `jit_kernels/impls/sm90_fp8_fp4_gc_moe.py`）

1. **角色元组扩一位**。`_role_specs` 在 `config.sm_reuse` 为真时插入 role 6，
   顺序必须是 `(1, 5, 6, 2, 3)`（dispatch 先、finalize 后、其它唯一）：

   ```python
   if getattr(config, 'sm_reuse', False):
       roles = roles[:-1] + (6,) + roles[-1:]
   ```

2. **role 6 住在 dispatch 的 context 里**，而不是 compute 的：

   ```python
   # 同一个 graph，两个 green context
   _ctx_idx = 0 if (index == 0 or binary.role == 6) else 1
   ```

   dispatch 用的是 `contexts[0]`（6 SM 的 green context），role 6 也放这里，
   所以它只能拿到 dispatch 分区内的 SM。

3. **graph 依赖 = 同步原语**（没有 host 参与、没有额外 kernel launch）：

   ```python
   # role 6 的唯一前置是 role 1；只有在 pull 完成、dispatch 的 24 个 CTA
   # 全部 return 之后，6 个 SM 才空出来，role 6 的 6 个 CTA 才可被调度。
   _prereq = (1,) if binary.role == 6 else prerequisites
   ```

   ★ 这一步很关键：如果让 role 6 做 graph 的**根**，它会和 dispatch 同时驻留，
   而 dispatch 的 24 个 CTA 需要 5 个 SM、role 6 每个 CTA 要 199680 B（1 CTA/SM）,
   11 个 SM 塞不进 6 个 SM 的 context ⇒ **死锁**。用依赖关系把两者串起来是唯一可行的排布。

4. **grid = dispatch 分区的 SM 数（6）**，不是 dispatch 的 CTA 数（24）：

   ```python
   _part = schedule_sms if schedule_sms else 6      # GC_MOE_SM90_DISPATCH_PARTITION_SMS
   _grid6 = max(1, _part)                           # = 6
   ```

   实测过 `_part * occupancy`（12 个 CTA，`tile_m=32`）会死锁：
   6 个 SM 被塞满后，**同一 context 里下一次调用的 dispatch 没有共享内存可调度**，
   报 `No available shared memory broadcast block found in 60 seconds`。
   1 CTA/SM 是这台机器上的硬上限。

5. **role 6 的 kernel 体就是 role 2 的 `_compute_persistent`**，只把入口线程号整体
   平移 128（`_reuse_helper_entry`），因为 `_compute_sync` 假设 `tid>=128` 是数学半区、
   `tid<128` 是生产者半区，而 role 6 整个 CTA 都是数学。任务队列、
   `active_ready`/`expert_ready` 协议、`l1_done` 计数全部与 role 2 共享，**零额外通信**。

6. **没有"等待"循环**。旧版在末尾写 `wait_epoch(header, epoch + 1)`，
   role 6 会一直堵到本层 combine 结束 —— 它和 dispatch 共 context，于是
   **下一次调用的 dispatch 起不来**（实测 `warm` 73.9 → 142.8 ms，`prefill` 76 → 146 s）。
   现在算完即返回，靠 graph 依赖做同步。

### 领任务的退出条件（必须按 call 生命周期，不能按 `header[9]`）

role 6 启动时 `dispatch_done == epoch` **已经成立**，所以 role 2 的退出条件

```python
while active_slot >= active_count and dispatch_done != epoch:   # role 6 一进来就是 false
```

会让它在第一个越界 task 上**直接退出**（实测 BS=256：850 µs 停下、只吃 72 块 = 4.1%）。
改成按 call 的生命周期自旋（`header[0]` 只在 combine 结束时推进）：

```python
while active_slot >= active_count and ld_acquire_gpu_u32(head) == epoch:
    active_count = ld_acquire_gpu_u32(head + 7)
```

修好后 BS=256（当时的 100 步窗口）：role 6 吃到 100 块（6.3%），且与 role 2 **同时结束**。

### 代价与边界

* **无额外通信**：role 6 用和 role 2 相同的 task 队列与 `active_ready`/`expert_ready`
  协议，不引入跨 rank 同步。
* **不改 task 粒度**：一个 task 仍是 `(槽, N-tile)`，它的所有 M 块由同一 CTA 处理。
  这很重要 —— 权重 TMA 地址是
  `index = (expert * n_size/256 + ntile) * k_size/128 + kb`，**不含 M 块偏移**，
  所以同一 N-tile 的多个 M 块复用同一份 640 KB 权重（L2 命中）。
  把 M 块拆到不同 CTA 会重复发 640 KB 的 HBM 读。
* **上限 = 6 个 CTA**：见上面第 4 点，塞满即死锁。
* **只吃尾部**：role 6 起来时 L1/L2 队列里还剩多少块，它就只能吃多少。BS 越大剩余越多，
  所以加速随 batch 单调增大。

   要判断「role 6 是否在尾部帮忙」，应看同一时间段的 `last 20%` 与
   `last 20% (role 2 only)` 之差：**四档都是 +4.3 / +4.4 / +4.0 / +4.3 个 CTA**，
   即 role 6 在整层都在出力、并不只是尾部。
3. **并行度不是越高越快，要看「做多少活」**：`CTA·µs`（并行度对时间的积分）

   `eco` 高 **51%**。⇒ 并行度曲线只能解释「同样的工作跑得多满」，
   工作量本身由放置质量决定。

### 结论一：拖尾的永远是**行数最多的那个槽**（BS ≥ 64）

除 BS=32 外，**20 个 run 里有 16 个的最后一个块来自该 rank 行数第 1 的槽**：

| BS | eco 的拖尾专家（行数/块数/末块 valid）| eco_smr 的拖尾专家 |
|---:|---|---|
| 32 | e170（8 行，1 块，valid 8）| e128（16 行，1 块，valid 16）|
| 64 | e264（24 行，1 块，valid 24）| **e237**（32 行，1 块，valid 32）|
| 128 | e205（16 行，1 块，valid 16）| **e35**（72 行，2 块，末块 valid 8）|
| 256 | **e237**（112 行，2 块，末块 valid 48）| **e237**（128 行，2 块，末块 valid 64）|

BS=32 例外：每 rank 每层只有 24 个 token（4 seq × topk 6 / 8），最大的槽也只有
8–24 行，全层只有 18–21 个 M 块，**谁都只有一块**，所以谁最后结束基本是调度噪声。
从 BS=64 起规律非常稳定：**热点专家 = 行数最多的槽 = 拖尾者**。

### 结论二：拖尾的直接原因是 **L2 的 20 个 N-tile 只能串行等**

以 BS=256 的 `eco_smr` 为例（e237、2 个 M 块、128 行）：

```
slot48 (e237, 128 rows, 2 M blocks) 的完整时间线：
  pull 完成                     :  117 µs
  block0 的 18 个 L1 tile      :  348 – 417 µs（结束）   <- 65 个 CTA 在跑
  block1 的 18 个 L1 tile      :  401 – 470 µs（结束）
  L1 全部完成（该专家）         :  470 µs
  block0 的 20 个 L2 tile      :  589 – 618 µs（结束）   <- 只剩 ~17 个 CTA
  block1 的 20 个 L2 tile      :  614 – 643 µs（结束）
```

最后 **29 µs**（占整层 4.5%）整个 GPU 只有 **20 个 CTA** 在跑这 20 个 L2 N-tile。
原因不是放置，而是 `hidden/256 = 20`：**L2 的 N-tile 数固定为 20**，
一个块的 L2 最多只能并行 20 路，哪怕另外 51 个 CTA 空着。

★ 顺带一个必须说清的事实：**e237 的 L1 与 L2 之间隔着 ~120 µs**
（block0 的 L1 在 417 µs 就结束，它的 L2 到 589 µs 才开始）。这不是调度延迟，
而是 `wait_count(l1_done[expert], intermediate/128)`：L2 必须等**该专家所有
M 块**的 L1 都完成。slot48 的 block1 L1 到 470 µs 才结束，而 e237 在该 rank 上
只有 slot48 一个槽，所以 L2 被这一块拖到 589 µs。

那 120 µs（470–589 µs）**并行度是 62.3 个 CTA，全层第二高** —— 也就是说
CTA 一直在算别的专家，并不是空闲。真正塌陷的只有最后一段：

| 区间 | 平均在跑 CTA |
|---|---:|
| 470–589 µs（e237 等 L1）| 62.3 |
| 589–643 µs（只剩 L2）| **44.2** |
| 614–643 µs（最后一块的 L2）| **17.3** |

再看 L2 窗口本身：589 µs 之后还有 **126 个 task** 没跑完，
但它们只来自少数几个专家的 L2，而这几个专家的 L2 N-tile 数各自只有 20 个。

### 结论三：这个尾部是**结构性**的，SM-reuse 只能部分抵消

`avg CTAs then` 一列显示，同一个块的 L1 窗口与 L2 窗口的并行度差距：

| BS | vanilla | eco | eco_smr |
|---:|---|---|---|
| 32 | 58.5 → 46.2 | — | 45.6 → 37.1 |
| 64 | 60.5 → 47.5 | 63.0 → 41.5 | 50.1 → 48.0 |
| 128 | **66.0 → 15.6** | 61.6 → 45.8 | **60.3 → 12.0** |
| 256 | **59.0 → 9.9** | 62.5 → 26.3 | **65.5 → 17.3** |

* `block_m=64` 的大档（BS=256）L2 窗口只剩 **10–17 个 CTA**，因为一层只有
  48–62 个 M 块、而 L2 的并行度上限是 20。
* `eco` 的 L2 窗口比 `vanilla` 好一倍（26.3 vs 9.9），因为它的 48 个块更分散、
  L2 的释放时刻错开，不容易全部压在最后一瞬间。
* SM-reuse 的 6 个 CTA 在这 20–30 µs 里是**唯一还能增加并行度的来源**，
  这也是它 −1% 量级收益的来源；但要彻底消掉这个尾巴，必须改
  **L2 的 N-tile 粒度**（例如把 `hidden/256` 拆成 `hidden/512`），那属于另一个改动。

### 结论四：`random` 的尾部最糟，是因为它的热点槽被切成了 3 块

BS=256 `random`：拖尾专家 e37，该槽 **184 行**、被切成 **3 个 M 块**
（末块 valid 56），L2 窗口从 813 µs 持续到 844 µs（31 µs），期间平均
只有 55.5 个 CTA。它的 `rows` 是 `eco` 的 1.64 倍、块数是 1.5 倍，
**这就是它整层 ms 慢 7.4% 的微观来源**：不是并行度低，而是活多。

## ★ EPLB 的 IR 为什么降得少：按算法模拟重排前后的 IR

问题：实测 EPLB（`rr`）把 BS=256 的 `excess = IR − floor` 只从 0.306 降到 0.229
（**25%**），而 ECO 能降到 0.143（**53%**）。是放置算法弱，还是别的？

### 先分清「可优化的部分」

`IR = max_r tok[r] / mean_r tok[r]`，而每个 (step, layer) 的每 rank token 数是一次
**多项分布抽样**，所以即使放置完美，`max/mean` 也会大于 1：

$$ \text{IR}_{\text{floor}} \approx 1 + \frac{1.42}{\sqrt{m}}, \quad m = \text{每 rank 每层每步的 token 数} $$

| BS | m | floor | vanilla IR | rr IR | eco IR |
|---:|---:|---:|---:|---:|---:|
| 32 | 24 | 1.2899 | 1.4769 | 1.4439 | 1.3833 |
| 64 | 48 | 1.2050 | 1.4532 | 1.3780 | 1.3586 |
| 128 | 96 | 1.1449 | 1.4161 | 1.3479 | 1.3014 |
| 256 | 192 | 1.1025 | 1.4089 | 1.3314 | **1.2451** |

⇒ 扣掉 floor 之后，**`rr` 只去掉了 25–30% 的系统性不均衡，ECO 去掉 41–53%**。

### 用真实直方图模拟「同一个 planner，喂不同的输入」

脚本 `scripts/sim_eplb_gain.py`：从 trace 的 `type 2`（每槽拉取行数，8 个 rank
求和后除以 8 去掉 world 膨胀）+ EcoMeta 的 slot→expert 映射，重建出**精确的
每专家需求直方图**，然后用同一个 `rebalance_experts_global` 生成放置，再用与
kernel 相同的 IR 定义评分。

| run | m/rank | floor | **before**（identity）| **after（1×1×E，现在的做法）** | after（每步直方图）| 计划过期（warm 与 measure 分布不同）| 实测 IR |
|---|---:|---:|---:|---:|---:|---:|---:|
| BS256 eco | 122.8 | 1.1282 | 1.3632 | **1.1162** | 1.0527 | 1.1652 | 1.2451 |
| BS256 rr | 67.2 | 1.1732 | 2.9781 | **1.1394** | 1.0667 | 1.2080 | 1.3314 |
| BS256 vanilla | 97.0 | 1.1442 | 2.3256 | **1.1209** | 1.0624 | 1.1543 | 1.4089 |
| BS128 eco | 39.6 | 1.2256 | 1.3038 | 1.1996 | 1.0936 | 1.2208 | 1.3014 |
| BS64 eco | 19.6 | 1.3205 | 1.8369 | 1.2167 | 1.1314 | 1.3094 | 1.3586 |
| BS32 eco | 8.4 | 1.4907 | 1.8806 | 1.3192 | 1.1888 | 1.6046 | 1.3833 |

**三个结论**：

1. **算法本身没坏。** 只要喂给它一个和评分窗口**同分布**的直方图，`1×1×E`
   就能把 BS=256 的 IR 从 1.363 压到 **1.116**（floor 是 1.128 —— 已经到极限），
   BS256 的 `rr` 甚至能从 2.978 压到 **1.139**。也就是说 **同一窗口下的理论收益
   是 68–93%**，而不是实测的 25%。
2. **真正的损失在「计划过期」。** 把 plan 用**另一份**泊松抽样算出来、再在
   目标流量上评分，IR 就从 1.116 涨到 **1.165**（BS256）；损失随 batch 变小而
   放大（BS32：1.319 → **1.605**）。

   ★ 代码层面已确认运行时就是这种情形：

   ```python
   # scripts/real_decode_100_100.py
   [warm] 1000 decode steps                      # <- stats 在这里累加
   engine.collective_rpc('_gc_moe_rearrange')    # <- 用 warm 的 stats 规划
   # integration/deepep_compare.py L1214
   mod._eplb['stats'].zero_()                    # <- 规划完立刻清零
   [measure] 1000 decode steps                   # <- IR 在这里计分
   ```

   所以「规划 → 计分」之间隔着 **一次权重搬迁 + 两个 1000 步窗口的分布漂移**。
   注意 stats 是**逐层**的（`table[idx]`，idx 是层号），所以层维度是保留的；
   被压掉的是**步**维度（`demand.view(1, 1, experts)` 把整个窗口折成一个合成
   step）—— 这也是结论 3 的来源。
3. **喂 `1×1×E`（把 40 层折成一个合成 step）不是主因，但也不是无害的**：
   在 BS256 上它和「每步直方图」只差 1.116 vs 1.053（约 6% 的 excess），
   因为 `sum_steps max_rank` 这个目标被折成 `sum` 后确实分辨不出「时热时冷」的
   专家；而 BS32 上两者几乎一样（1.319 vs 1.189，差别主要在噪声）。

$$
\boxed{
\begin{aligned}
&\text{同窗口理论上限} && \text{IR } 1.363 \to 1.116 \;(\text{去掉 } 68\%)\ \
&\text{暖/测窗口分布漂移} && 1.116 \to 1.165 \;(\text{吃掉 } 46\% \text{的收益})\ \
&\text{实测} && 1.245 \;(\text{只去掉 } 32\%)
\end{aligned}}
$$

⇒ **要真正降 IR，优先级是：① 缩短「规划→计分」的间隔（或按 measure 流量在线重排），
② 再把 `1×1×E` 换成真正的逐步直方图。** 单纯换更强的放置算法收益有限 ——
在 BS256 上算法已经能贴到 floor 了。

## ★ 副本槽拉取插入时机的影响（延时扫描，BS=256，放置冻结）

**问题**：副本槽要等 plan 发布 quota 才能开拉。如果让它们更晚开始，会不会改善流水线？

**方法**：在 plan 算完 quota 之后、`release(eco_ready[1])` 之前插入一段自旋等待
（`GC_MOE_ECO_PLAN_DELAY_US`，编译期常量），把副本槽的开拉时刻按 10 µs 一档往后推。

**为什么冻结放置**：不冻结时每档的 EPLB 重排结果不同（`phy2log` 8 档全不同），
M 块数从 22 抖到 37，无法分辨延时本身的影响。冻结（`GC_MOE_EPLB_REARRANGE=0`，
用 `initial_layout`）后：

* 连续两档同配置复现误差 **< 0.05%**（71.02 vs 71.00）
* 代价：绝对性能从 65.80 → 71.02 ms（**+8%**），因为 initial_layout 不是最优放置。
  ⇒ **这组数据只能看相对变化，不能与 16 臂表比绝对值。**

### 分阶段耗时（BS=128，µs/次 MoE 层调用，8 rank 平均）

> ℹ️ 本节与下一节的数据来自 `CB4_128_*`（2026-11-08），分阶段数值是 **trace 相对量**，

> 但它们对比的是**旧的 71-CTA ECO**，绝对 ms 数值请以顶部重测表为准。

两臂都开 `GC_MOE_ECO_TRACE=1`（`runs/CB_128_*.json` / `runs/CB4_128_*.json`）：

| 阶段 | 原生 | eplb+eco | 差 |
|---|---:|---:|---:|
| push | 7.1 | 9.5 | +2.4 |
| pull 跨度（首槽开始 → 末槽完成） | 76.2 | 81.2 | +5.0 |

* 也就是说 **ECO 的 dispatch 比原生慢**，收益必须从别处找 —— 下一节是答案。

### ★ 收益来源：combine 更快，不是 dispatch 更快（BS=128）

两臂同一张 `pull_tl` 表（早期 `eco_trace` 只在 ECO layout 里分配，vanilla 拿不到 combine，
所以把 combine 首/末标记并入了 `pull_tl` 的 slot 8/9）。覆盖 8 rank × 256 层调用 × 2 臂 =
2048 行，slot 全部命中且有序。

| 阶段（µs/层，中位数） | 原生 | eplb+eco | 差 |
|---|---:|---:|---:|
| push_end → pull_begin | 3.0 | 4.0 | +1.0 |
| **PULL** | **74.0** | **82.0** | **+8.0** |
| pull_end → combine_begin | 338.0 | 349.0 | +11.0 |
| **COMBINE** | **193.5** | **152.0** | **−41.5** |
| push_end → combine_end | 625.0 | 603.0 | **−22.0** |

combine p90：原生 449 → ECO **354** µs ⇒ 尾巴短 95 µs。

**结论**

1. **ECO 的 dispatch 每一档都更慢**（BS=128 时约 +10~14 µs/层 = 0.5 ms/step）——
   多 8 个副本槽 + 一份 plan，这是固定开销。
2. **ECO 的 combine 快 21%**（−41.5 µs/层）。副本把每 rank 的入站 token 摊薄，
   scatter/归约跨度变短，尾部尤其明显。
3. 净差 `push_end → combine_end` = **−22 µs/层 ≈ −0.88 ms/step**，与实测 −1.09 ms 同量级
   ⇒ **ECO 的收益在 combine，不在 dispatch。**
4. ~~这也解释了「ECO 只在大 batch 赢」~~ **该结论已被 2026-11-09 重测推翻**：
   修掉 half-SM bug 后 ECO 在 BS=32 也基本打平（+0.39%），BS≥64 全胜。
   旧数据里「BS=32 原生最快」是 ECO 只用 36/72 SM 造成的假象。

### TMA token 拉取（上游 SM90 的遗留瓶颈）

上游 `Bruce-Lee-LY/gc-moe` 的 SM90 里，**token 拉取仍是 16 B 同步拷贝**
（`copy_global_16`），而 SM100 用的是 TMA（`bulk_g2s_1d`）。权重两边都是 TMA ——
也就是说 SM90 移植时把数据量最大的 token 路径漏掉了。

实测该路径只有 **4.4 GB/s**。改成 SM100 的 TMA 结构后：

| 臂 | TMA 前 | TMA 后 | 变化 |
|---|---:|---:|---:|
| random+rr | 81.76 | **71.33** | −12.8% |
| eplb+rr | 73.28 | **66.56** | −9.2% |
| eplb+eco | 75.55 | **66.47** | −12.0% |

`pull_norep` 305 → 124 µs（−59%），`pull_rep` 373 → 142 µs（−62%），
带宽 4.4 → **10.7 GB/s**。

三个死锁级约束（都已解决）：dispatch 的 smem 必须 ≤ 58368 B 才能 4 CTA/SM 驻留
（双缓冲 84864 B 会导致 grid 会合永远等不齐）；`mbarrier` 的 phase 必须存在
shared memory（staged 循环里 Python 变量每次迭代都会重置）；`mbarrier_init_fence()`
不可省。

## ★ 三个开关（相互独立）与新的 IR 口径

这个目录把三件事做成**互不依赖的 env 开关**，可以任意组合：

| 开关 | 作用 | 依赖 |
|---|---|---|
| `GC_MOE_EPLB=1` | EPLB 放置（副本），`GC_MOE_SLOT_PLACEMENT=random` 换成随机放置作对照 | — |
| `GC_MOE_ECO=1` | 内核内 plan（role 5），副本按配额切分流 | 需要 `GC_MOE_EPLB=1` |
| `GC_MOE_SM90_SM_REUSE=1` | role 6：dispatch 拉完后把 6 个 SM 交给 compute | 需要 `GC_MOE_ECO=1` |

`apis/sm90_gc_moe.py` 直接从环境读这三个值，所以 `run_arm_eco.sh` 只需要 `export`，
不需要改脚本。role 6 的 CTA 数默认等于 dispatch 分区的 SM 数（6）；

一条命令跑五臂（含 sm_reuse）：

```bash
# 产出 runs/IR32_{vanilla,random,rr,eco,eco_smr}.json
```

### 为什么换了一个 IR 定义

旧口径把 100 步的计数**先求和再算** `max_rank/mean_rank`。求和会让各 rank 的
偏离互相抵消，而 `max/mean` 不是线性泛函 —— **逐步的真实不均衡无法从窗口求和里恢复**。
一个极端例子（CPU 已验）：

```
4 步、每步都只有一个 rank 是 3x：
  逐步 IR = 2.00  （每步 max/mean = 300/150）
  窗口 IR = 1.00  （4 步合计每个 rank 恰好相等）
```

新口径（`ir_step`）**每层每步各算一次**，再把所有 `(step, layer)` 对取平均：

```python
for step, layer:
    IR = max_r tok[r, step, layer] / mean_r tok[r, step, layer]
ir_step_layer_mean = mean(all pairs)
```

同时给出 `ir_step_layer_p50/p90/p99` 与 **Poisson 零假设基线**
（`ir_poisson_null_mean`）：单层单步每个 rank 只有约 192 条路由，
`sigma = sqrt(192) ≈ 13.9`（7.2%），即使放置完全均衡，`max/mean` 也会 > 1。
**只有 `ir_excess_over_null` 才是放置真正贡献的部分。**

采样方式：decode 会重放 CUDA graph，引擎自己无法逐步采样，所以由测试脚本
在**计时窗口之后**另开一个窗口，每步发一次 `_gc_moe_irstep_sample`
（RPC 约 60 ms，因此**不计入 ms/step**）。结果写在 run json 的 `ir_step` 字段。

### [EPLB-FIX] 一个 logical expert 不能有两个副本落在同一 rank

`eplb_placement.py` 的模块注释一直写着"the packer is never allowed to place a
physical expert back on its home rank"，但 `_pack()` 只做了负载均衡，**没有落实这条约束**。
实测（`physical=448, ranks=8`）：64 个被复制的专家里有 **5 个两个副本都在同一个 rank**
（4/rank 的 424 槽布局是 3 个）。

后果有两个，都是实测到的：

* 重复的那个副本是 **passive**（`_eco_is_active == 0`），它不拉任何 token，
  有效冗余悄悄从 64 缩到 59；
* `replica_ranks[logical]` 塌缩成单个 rank，该专家根本没有第二个 rank 可以分流量
  —— plan 算出来的 split 无处可去。

修法（`source/gc_moe/layout/eplb_placement.py`）：

1. `_pack()` 接收每个槽的 logical id，分配时排除**已经持有该专家副本**的 pack；
2. `logcnt[e]` 上限设为 `ranks`，否则贪心"最热优先"会给单专家 9 个副本，
   而 8 个 rank 无论如何都会撞车（偏斜负载下实测触发）。

回归测试：`tests/test_eplb_placement_cpu.py`（6 个用例，含两个偏斜负载）。

⚠️ 这个 bug 影响**之前所有 EPLB 实验**（16 臂 / 20 臂 / 四臂）的绝对数值。

## ★ 本轮夜间任务结论（2026-11-13）

### 1. plan 的无侵入性：成立（trace 直接测量）

在 ECO 臂打开 `GC_MOE_ECO_TRACE=1`，`eco_tl` 每层每步一行，直接读出 plan 各段耗时
（BS256，k=8，1000+1000，2048 个 call = 40 层 × 1000 步 × 8 rank 抽样）：

| 段 | mean (µs) | p90 | 占比 |
|---|---:|---:|---:|
| 等 counts (2→3) | 5.95 | 9 | 15.3% |
| **静态表 (3→4)** | **13.15** | 16 | **33.8%** |
| cold/warm (4→5) | 7.22 | 9 | 18.6% |
| auction (5→6) | 8.51 | 14 | 21.9% |
| publish (6→7) | 4.09 | 5 | 10.5% |
| **合计 (2→7)** | **38.91** | 47 | 100% |

关键：**plan 几乎全部被单副本 pull 窗口掩盖**

- push 开始相对 plan_start：+5.07 µs
- 第一个单副本槽开始 pull：**+20.48 µs**
- 第一个副本槽拿到 plan：**+32.42 µs**
- **2048/2048 个 call 中，plan 都在单副本 pull 开始之后才结束，平均滞后 18.4 µs**

⇒ 38.91 µs 里约 20 µs 与单副本 pull 完全重叠，只有 ~18.4 µs 暴露在关键路径，
而这 18.4 µs 还会被单副本 pull 的剩余时间继续掩盖。
**⇒ 不需要优化 plan 本身**；静态表 13.15 µs 是 plan 内最大单项（将来要压先压它）。

⚠️ 顺带否掉一条捷径：**host 预写 quota 不能替代每步 plan**。
`rearrange_now` 只在 warm 后调用一次，host 算的 quota 于是变成常量，
1000 个 measured step 全用同一份 ⇒ IR 从 1.0262 劣化到 1.2014，
ms 从 69.14 劣到 75.91。要测 plan 的无侵入性必须用
`GC_MOE_ECO_TABLE` 的 capture→replay（同一进程、同一 token 流）。

### 3. 一个潜伏很久的真 bug：`id()` 回收让 40 层挤进同一行

`_launch` 每层每步用 `id(packed[0][0])` 反查该层的计数器行号。
`id()` 只在对象存活期间唯一，而映射表是在**另一条代码路径**（安装阶段）建的，
一旦中间有 tensor 释放，id 被回收后就会串行。症状：

```
per_layer_median_tokens = [0, 0, ..., 159.7]   <- 只有一层有数据
per_slot_token_sum     = 只有 5-6 个槽非零
```

### 4. 「大槽先拉」不成立（已放弃）

两次同配置对照，BIG=1 的收益符号都翻了，且都更慢：

| 跑次 | BIG=0 ms / ir | BIG=1 ms / ir |
|---|---|---|
| 第 1 次 | 68.31 / 1.0338 | 70.70 / 1.0176 |
| 第 2 次 | 68.95 / 1.0288 | 73.13 / 1.0343 |

排序本身 ~1-2 µs/call，而它想消掉的尾部在 BS256 下已被 71 CTA 的并行度自然填满。
代码保留在隔离环境（`GC_MOE_SM90_PULL_BIG=1` 才启用，默认 0 与原行为等价）。

★ 但排查过程中找出 **2 个真 bug**：① `pull_order` 是全局数组、只有 block 0 写，
其他 CTA 过了 CTA-local barrier 就读到半成品；② 只置换了 `global_slot` 而没置换
循环变量 `expert`（`expert_count`/`stats`/`route_meta`/`l1_acts` 全按它索引），
于是「拉了槽 X、写进第 Y 行」。第二个一直潜伏在 6 个隔离环境里，
直接导致 ECO 臂放置崩坏（`max_copies=53`）——这是本轮最有价值的产出。

#### 并行度实测：为什么它不成立

两次对照都没有开 trace，所以补跑了一组**两臂都开** full trace
（`GC_MOE_ECO_TRACE=1 GC_MOE_PULL_TRACE=1 GC_MOE_FINE_TRACE=1`，
`GC_MOE_FINE_MIN_EPOCH=20000` 锁在重排之后，BS=256，1000+1000）：

| 臂 | ms/step | ir_win | 单层 makespan | plateau(mid 50%) | last 20% | pull 全部完成 |
|---|---:|---:|---:|---:|---:|---:|
| BIG=0（原顺序） | **68.75** | **1.0253** | 678 µs | 72.4 | 60.1 | 108 µs |
| BIG=1（大槽先拉） | 71.72 | 1.0325 | 646 µs | 71.8 | 57.6 | 106 µs |

![compare](docs/t4/compare_parallelism_BIG0_vs_BIG1.png)

单臂图（含逐 CTA 甘特）：[BIG=0](docs/t4/par_T4L2_BIG0_rank0.png) ·
[BIG=1](docs/t4/par_T4L_BIG1_rank0.png)

**并行度曲线几乎重合，这解释了为什么它没有收益：**

1. **pull 早在 108 µs 就全部结束了**，而整层要跑 678 µs —— pull 只占 16%。
   重排 pull 顺序最多只能影响这 16% 里的负载分布，动不了剩下的 84%。
2. **中间段（位相 100–600 µs）两臂都在 71–77 CTA**，即 role-2 的 71 个 CTA
   加 role-6 的 6 个已经基本打满。原顺序并没有在中间段制造空闲。
3. **尾部塌陷两臂都有**，BIG=1 甚至略差（last 20%：57.6 vs 60.1 CTA）。
   原因是尾部由"最后几个 M 块"决定，而不是"哪个槽先被拉"——
   按 token 数排序**并不能**把尾部的小任务提前。
4. 单层 makespan BIG=1 反而短 32 µs，但 ms/step 慢 3 ms：
   **两者不是同一个量**（单层采样 vs 2000 步平均），说明层间波动远大于这个差异，
   也说明这个"优化"落在噪声里。

⇒ 结论：**「大槽先拉」不成立**。它想修的尾部塌陷，其成因是 M 块粒度与
  N-tile 并行度（见"尾部并行度低，究竟是哪个专家/M 块在拖"一章），
  不是 pull 顺序。

* `GC_MOE_EPLB_EXTRA_PER_RANK=n` 直接设**每 rank** 的冗余槽数

  每 run 只记 4 万层调用中的 1 层。
