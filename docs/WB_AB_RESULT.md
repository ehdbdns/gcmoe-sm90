# 权重 A/B 结论：保留 wb=26，放弃 wb=34

## 实验条件（关键：公平性）

* 全部 `GC_MOE_MB_CLAIM=0`（历史领取粒度），因此**权重差异不会被并行度改动污染**
* 其余与 20 臂主表一致：`WARM=1000 MEASURE=1000`、`EXTRA_PER_RANK=8`、
  `PULL_TMA=1`、`GC_IRSTEP_STEPS=1024`、开 trace
* 模型走本机副本 `/home/admin/local_models/DeepSeek-V4.1-Flash`，
  权重加载稳定在 20–23 s（走 NAS 是 317 s）
* 共 16 个 run = 4 档 BS × 2 臂（eco / eco_smr）× 2 权重（26 / 34）

**关闭路径复现性验证**：`A26_B256_eco` = 61.875 ms，
历史基线 `AT256_eco`（改动前源码）= 62.394 ms，差 0.8%。
说明 `GC_MOE_MB_CLAIM=0` 确实回到了历史行为，A/B 可信。

## 判定（按任务书事先写好的规则）

规则：新权重需在 **≥3/4 个 BS 上 ms 更低** 且 IR 不劣（ΔIR < 0.005）。

* **ms：wb=34 只在 2/8 个对比里更低**（BS64-eco、BS128-eco_smr），
  且这两处收益很小（−0.14%、−1.53%），其余 6 处更差。
* **IR：wb=34 在 8/8 个对比里全部更差**，ΔIR 范围 +0.0052 ~ +0.0270，
  且**小 BS 恶化最严重**（BS32 的 +0.019/+0.027 是大 BS 的 3~5 倍）。

⇒ **不满足条件，保留 wb=26、wa=0。**

## 为什么 wb=34 反而更差（诊断）

wb 越大，ECO 越"害怕"多开一个 M 块，于是把 token 更集中地塞进已有槽位。
但实测（见 `VALID_COST.md`）每个 M 块的耗时是
`427 + 14.5·nq`（纯 GEMM），**固定项只占 25%~35%**，
而 token 项是线性增长的 —— 把 token 堆进同一个槽位会让该槽位变成
串行长链，反而拉高 max_rank。

trace 里那条价值 69 µs/块的"任务间空白"虽然真实存在，
但它同时会被**多块并行**摊薄：拆成 2 个块时空白并行发生，
而 wb=34 会主动避免拆分，等于放弃了这部分并行收益。
**所以空隙开销不该按"串行 38 次"全额计入 wb。**
这是 v2 推导（`WB_FIT_V2.md`）的系统性偏差，这一轮 A/B 把它证伪了。
