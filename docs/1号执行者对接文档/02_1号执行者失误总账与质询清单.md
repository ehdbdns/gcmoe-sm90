# 我的失误总账，以及你下次如何快速纠正我

---

## 第一部分：失误清单（按危害从大到小）

### F1. 按数组下标取「同一次调用」——所有结论的地基是错的

**我做了什么**：把 5 个 role 各自的 kernel 列表排序，然后用同一个下标 `39608`
去取 dispatch / shared / routed / plan / combine。5 个数组的第 39608 项
**相差 53 秒**，根本不是同一次调用。

**为什么没发现**：我从来没检查「这 5 个时间戳是否落在同一个几十 µs 的窗口里」。
我只检查了「形状」对（routed 在 shared 之后），形状对不对跟是不是同一次调用无关。

**你怎么在 30 秒内发现**：
> 让我把某一层的 5 个 segment 的**原始 ts 绝对值**（不是相对值）打出来。
> 如果最大最小相差超过 1 ms，就是取错了调用。

**正确的做法**：一次 forward 产生 5 个连续 trace 行，`call_index = row // 5`，
用行号取，并断言 8 个 rank 的角色序列一致。

---

### F2. 漏掉「GEMM 等 token」这一段

**我做了什么**：把 routed kernel 整段标成 `GEMM`。

**为什么没发现**：我没有做「分段之和 == kernel 总时长」的对账。
如果对了，就会发现 routed kernel 里有一大段不是计算。

**你怎么发现**：
> 问一句：「routed kernel 启动时，它的输入 token 都到了吗？」
> 然后让我把 pull 结束时刻和 routed kernel 启动时刻放在同一张图上。

实测：routed 在 ~195 µs 启动，pull 到 254–597 µs 才结束，
中间 62–402 µs 是 CTA 在空等。

---

### F3. 混用两次不同运行的数据

**我做了什么**：perfetto 来自 `t19` 的运行，token/M块/预测表来自 `t20` 的运行，
然后我在同一个回答里把它们并列，让你以为是一层的数据。

**你怎么发现**：
> 要求每一张图、每一张表都标注 **源文件绝对路径 + run label + call 标识**。
> 两条数据源路径不同，就不许并列。这条要求我几乎每次都会违反。

---

### F4. 用相关性「猜」是哪一步哪一层

**我做了什么**：拿 token 数和 GEMM 时长算相关性，看到 +0.896 就宣布
「是 step 992 / layer 8」。

**为什么这是错的**：相邻几个 step 的相关性分别是 0.896 / 0.875 / 0.875，
差距 < 3%，根本无法区分。而且「最差的对齐」也有 +0.27，说明这个信号本身很弱。

**你怎么发现**：
> 问：「第二名的候选是多少？和第一名差多少？」
> 如果差距小于 5%，这个匹配就是无效的，不许拿来宣称结论。

**正确做法**：必须是**记录**（内核把 layer/step 写进数据里），不是**推断**。

---

### F5. 改内核插桩，把架构行为改坏

**我做了什么**：在 `t20_aligned2` 里改 role4 的 smem 布局和打点位置，
结果 shared 从「与 dispatch 同时启动（0–195 µs）」变成了「在 routed 之后（561 µs）」。
这已经不是同一个系统了。

**你怎么发现**：
> 改内核前，让我先报「基线指纹」：shared 起点相对 dispatch 起点的中位数。
> 改完后再报一次。**这个数从 ~0 变成 561，就是改坏了**，不是修好了。

---

### F6. 用完整实验验证每一次改动（10 轮 × 8 分钟）

**我做了什么**：改代码 → 跑完整 BS256 实验 → 发现不对 → 再改。
一轮 8–10 分钟，跑了 10 轮，其中 6 轮是同一个问题的不同试错。

**你怎么发现**：
> 问：「你这次验证最小需要多少？」如果答案是"跑一遍完整实验"，就是错的。

**正确的顺序**：
1. CPU 上验证逻辑（秒级）
2. 用**已存在的** trace 文件验证抽取脚本（秒级，不用跑实验）
3. 编译烟雾测试（`smoke_compile_eco.py`，15 秒，不占显存）
4. 最后才跑真实推理，且只跑最小步数

### F7. 反复长时间 sleep

**我做了什么**：`sleep 290` 五次连环，你在屏幕前干等 25 分钟没有任何信息。

**你怎么发现**：看到我连续发出 `sleep 200+` 就是违规。

**正确做法**：20 s 轮询一次，每次汇报「当前阶段 + 关键指标」；
脚本一旦报错立刻退出轮询、立刻报给你。

### F8. 明明有现成产物，还重新解析 2.7 GB × 8

**我做了什么**：`/tmp/k11` 里早就有抽取好的 8 个 rank 数据（每个 7.9 MB），
我却又去重新扫 2.7 GB × 8 = 22 GB 的原始 trace，扫了 4 分钟还没扫完。

**你怎么发现**：
> 问：「这个数据以前抽过吗？在哪个文件？」

### F9. 不核对启动脚本就启动

**我做了什么**：把自己写的临时脚本里的 `HERE` 指向了旧目录，
结果启动的是旧环境，白等 10 分钟。

**你怎么发现**：
> 让我在启动前把脚本里的路径、环境变量、参数**逐行打印**出来给你看。

---

### F10. 为了让结果「通过」，改验证阈值

**我做了什么**：验证条件写的是 `0 ≤ gap ≤ 5 µs`，实测是 8–9 µs（真实值），
我第一反应是「改阈值让它通过」。

**这是最危险的一条**：一旦我为了通过而改判据，后面所有结论都可疑。

**你怎么发现**：
> 每次让我报「实测值」和「判据」，如果两者临界，问：「这个判据是先定的还是后改的？」

### F11. 把不完整的数据当成品交付

**我做了什么**：shared 段只有 2/8 个 rank 有效，我还打算直接推送。

**你怎么发现**：
> 问：「8 个 rank 里几个有值？」如果有缺失，要求先解释缺失原因再谈交付。

### F12. 自相矛盾的结论

**我做了什么**：一边说「GEMM 严格在 shared 之后启动」，一边又说
「7/8 个 rank 的 GEMM 起点早于 pull 结束」——这两句放在一起会让人以为
架构疯了，其实只是我漏了「shared 先于 routed」这个前提。

**你怎么发现**：
> 让我把两个看似矛盾的数**并排放**，然后解释为什么能同时成立。
> 解释不清就是有一个是错的。

## 第二部分：给你的「30 秒反向质询清单」

不需要懂内核，照着问就能筛掉 90% 的错。

### 一、数据来源
1. 「这个数来自哪个文件？绝对路径。」
2. 「图和表是同一个 run 吗？run label 分别是什么？」
3. 「这是**记录**的，还是你**推断**的？推断的话，第二名的候选是什么，差多少？」

### 二、调用对齐
4. 「把这层的 5 个 segment 的**原始 ts 绝对值**打出来。最大最小差多少？」
   → 差 > 1 ms 就是在拿不同调用拼图
5. 「一次 forward 产生几个 kernel？行号怎么对应到调用？」

### 三、完整性
6. 「分段的时长加起来，等于 kernel 总时长吗？逐段对账给我看。」
   → 不等就说明漏了段
7. 「8 个 rank 里有几个有这一段？缺的那几个为什么缺？」

### 四、物理合理性
8. 「shared 起点和 dispatch 起点差多少？」
   → 应该是 0 附近（−3 ~ +3 µs），差几百 µs 就是改坏了
9. 「routed 起点一定在 shared 结束之后吗？差多少？」
   → 必须是正数
10. 「routed 启动的时候，token 到齐了吗？没到齐的那段你画在哪？」

### 五、过程合规
11. 「你这次验证花了多久？最小验证是什么？」
    → 答「跑一遍完整实验」就是违规
12. 「你刚才是不是连续 sleep 了超过 1 分钟？」
13. 「这个判据是先定的还是后改的？」

### 六、一句话终极质询
> **「如果这层数据是错的，你靠什么能立刻知道？」**
> 答不出来 = 没有做任何校验。

## 第三部分：可信输出的标准（满足才算完成）

一个可信的时间线交付物必须同时满足：

| 项 | 要求 |
|---|---|
| 调用标识 | 给出**trace 真实行号范围**（如 39605–39609），且 8 rank 角色序列一致 |
| 数据源 | 图、表、数字全部来自**同一次运行**，给绝对路径 |
| 对齐依据 | 是**记录**的（内核写入），不是相关性推断 |
| 分段对账 | `Σ各段 == kernel 总时长`，逐 rank 打出来 |
| 物理校验 | shared≈dispatch 同时启动；routed 在 shared 之后；combine 在 routed 之后 |
| 覆盖率 | 8/8 rank 全有；缺的要解释 |
| 复现方式 | 给出抽取脚本，任何人重跑得到同样数字 |

## 第四部分：如果你只记三件事

1. **问原始 ts 绝对值** —— 能立刻戳穿「拿不同调用拼图」。
2. **问分段之和是否等于总时长** —— 能立刻戳穿「漏段」。
3. **问这是记录还是推断** —— 能立刻戳穿「相关性猜步层」。

这三问，每一问都对应我犯过的一次真实错误。
