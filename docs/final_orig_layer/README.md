## 关键结论

**1. M块数 == 激活专家数**（表里两列完全相同）

`block_m=64`，每 rank 每层只有 184–206 个 token，摊到 22–32 个激活槽上，
平均每槽 6–9 个 token，**全部 < 64**，所以每个激活槽恰好产生 1 个 M 块。
**"激活了多少个专家"就是"M 块数"**，这是 route 决定的，不是放置决定的。

**2. valid 分布反过来补偿了块数差异**

| rank | M块数 | valid均值 | valid总和 | 实测耗时 |
|---:|---:|---:|---:|---:|
| 0 | 32 | 43.4 | 2 664 712 | 854 |
| 7 | 28 | **37.5** | **2 266 296** | **759** |

rank 0 块比 rank 7 多 4 个，单块 valid 也更大（43.4 vs 37.5），
valid 总和差 17.6%，实测耗时差 12.5% —— **两者方向一致且量级接近**。
这说明"块数 × 单块 valid"才是耗时的真实驱动量。

**3. 原始耗时函数的预测这次意外地准（L1 = 0.1063）**

`pred_ratio` 与 `meas_ratio` 的排序一致（rank0 最慢、rank5 最快都预测对了），
`maxerr = 0.0254`。

原因：这一层 rank 间的差异主要由**块数**造成，而 block_m=64 时块数 ≈ 激活槽数，
恰好在原始 cost 的 `wa` 项（每个激活槽一个固定成本）的建模范围内。
之前 `docs/origcost_layer_detail` 里 L1=0.33 的那次，取的是环形缓冲里 epoch 最大的一层，
不是同一层，且那次 `meas_us` 还是 256 次平均 —— 本目录的数据修正了这两个问题。
