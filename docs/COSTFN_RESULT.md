# 结论：实测耗时函数（去掉 token 项）在 8/8 对比中不如旧函数

## 实现（严格按用户三条要求）

### 1) 新耗时函数

```
nq(v) = GEMM 的量化档 8/16/32/40/48/64（不是 v 本身）

C_block(v) = 398.40 + 13.3203·nq(v) + 29.07 + 1.1510·v + 69.2
             └───纯 GEMM────┘  └──push──┘  └gap┘
cost(slot) = Σ_blocks C_block(valid_i)
```

* **无 token 项**（这是本次唯一的语义改变）
* push 用 `span − push` 拆出再加回，**不重复计**
* gap 用 **B 口径**（每块 38 次交接 = 69.2 µs），按用户要求

### 2) 改了 4 个同构点（缺一处就会自相矛盾）

| 位置 | 改动 |
|---|---|
| `_eco_costC` | 核心：`y·C(64) + hp·C(rem)`，token 项彻底移除 |
| `_eco_rank_time` | 同一模型按 slot 求和 |
| warm-start `unit` | 由 `wb+bm` 改为 `C_block(bm)` |
| cold key 每块边际价 | 由 `wb+bm` 改为 `(cf_gemm_nq+cf_push_v)·bm` |

`_eco_out` / `_eco_in` 是 `_eco_costC` 的差分，自动跟随。

### 3) 开关

`GC_MOE_ECO_COSTFN=1` 启用（默认 0 = 旧 token 式），两条路径均编译通过。

## 为什么"更贴近实测"的模型反而更差

这是本轮最有价值的发现。三个原因，按重要性排序：

### (1) token 项在 cost 里起的是"防串行长链"的作用，而不只是计时

旧 cost 的 `+ q` 会让"把 192 个 token 塞进一个槽"付出 192 的代价，
从而倾向**摊开**。新函数只按 M 块计费，而 `cost(72) = cost(64) + cost(8)`，
即**把 8 行塞进已有块 与 单开一个块 代价完全相同**。
于是 planner 失去了"避免零碎块"的倾向，反而更容易造出多块槽位。

### (2) B 口径的 gap 对排序几乎无影响，因此它不是失败原因

| valid | A 口径(1次gap) | B 口径(38次gap) |
|---:|---:|---:|
| 8 | 40.3% 满块 | 43.1% |
| 32 | 65.9% | 67.5% |

每块同加 69.2 µs，相对占比只差 2~3pt。
**换 gap 口径没有救回结果，说明问题不在 gap。**

### (3) 内核实际耗时与 cost 的相关性，弱于"块数"

实测每块耗时 `427 + 14.5·nq`：块内固定项只占 25~35%。
但整层的**墙钟**由 `max_rank(Σ cost)` 决定，而 rank 的墙钟里
串行块数是主导项（一个 3 块槽位 = 3×(1355µs) 串行）。
旧模型的 `wb=26/块 + 1/token` 恰好给出了"每块 26 + 每 token 1"的
近似权重比，而新模型把每块定价成 1355µs 等价物后，
`block:token` 的有效比从 26:1 变成了 ~1355:0（token 完全不计）。

## 落定

* 主表（`t18_abstrace` 的 20 臂，wb=26 wa=0）保持不变，仍是当前最优配置。
* `GC_MOE_ECO_COSTFN` 默认 0，代码保留以便后续再验证。
* 若要继续沿"实测函数"方向，下一步应保留 token 项、只把**系数**换成实测值
  （即 `wb_eff = 每块固定开销/每 token 开销`，回到 wb≈29.5 附近），
  而不是把 token 项设为 0。
