原始耗时函数（`GC_MOE_ECO_COSTFN=0`，`wb=26`、`wa=0`、末项 +token）下的
BS256（32 stream/rank）运行，1000 warm + 1000 measure，`GC_MOE_MB_CLAIM=1`，
CUDA graph 模式，shared expert 由 gc_moe role 4 计算。

- `ir_step.layer_detail` —— dispatch kernel 在设备侧记录的某一层 8 rank 明细
- `time_ir.plan_pred` —— 同一 epoch 的 8 rank 预测 cost 与实测耗时

## 这张表说明什么

**1. token 相对均衡，M 块却很不均衡**

| 量 | max/min |
|---|---:|
| token | 1.108 |
| M 块数 | **1.409** |
| 实际耗时 | 1.190 |

token 最多和最少只差 10.8%，但 M 块数差 40.9%。

原因：`block_m = 64`，而每个 rank 每层只有 ~190 个 token，摊到 22–31 个激活槽，
平均每槽 6–9 个 token，**都远小于 64**。所以 `M块数 == 激活槽数`
（表里两列完全相同），而"多少个槽被激活"对 token 的微小差异非常敏感。
token 从 185 涨到 205（+10.8%），激活槽就从 22 涨到 31（+40.9%）。

**2. 原始耗时函数的预测几乎没起作用**

预测比例全在 0.976–1.034 之间（跨度仅 6.0%），而实测比例在 0.963–1.147
（跨度 19.0%）。plan 认为 8 个 rank 几乎一样忙，实际上 rank 0 比 rank 7 慢 19%。

`L1 偏差 = 0.3335`，`maxerr = 0.1483`。

关键失误在 rank 0：预测 0.9984（几乎平均），实测 **1.1467**（最慢），差 0.148。
它的 token 只有 188（第 4 多），但激活槽 30（第 2 多），M 块 30（第 2 多）——
**原始 cost 的 token 项没捕捉到"槽数"这个真正决定耗时的量。**

**3. 换成查表版（`GC_MOE_ECO_COSTFN=1`）后**

同 BS256 下预测 vs 实测的 L1 偏差从 **0.3335 降到 0.103**（见
`docs/traces_layer_epoch14673`），因为它直接按 `M块数 × 单块耗时` 建模，
而不是按 token 数。

## 复现

```bash
# 采集：GC_MOE_IR_STEP=1 GC_MEASURE_IR_STEP=1 GC_IRSTEP_STEPS=1000
# 读取：runs/ORIGCOST_B256_V2.json 的 ir_step.layer_detail + time_ir.plan_pred
```

注意：`layer_detail` 是**第一个填满的 (layer, step)**，而 `plan_pred` 取
`pull_tl` 环形缓冲里 epoch 最大的那次调用。两者不保证是同一次调用，
所以本表的两组数并列时请按"同一 BS、同一配置的典型层"理解，而不是同一 epoch 的四个量。
