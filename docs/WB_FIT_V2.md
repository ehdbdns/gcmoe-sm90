# wb 重算 v2：把 combine push 与任务间空白计入

v1（`WB_FIT.md`）只用了 GEMM 的 task span，得到 `wb = 29.5`。
本轮按用户要求补两项，权重变了。

## 补的两项及其量化

### 1) combine push 随 **valid** 增长（不是随 nq）

push 的时长由真实行数决定，而 GEMM 按量化档 nq 收费 —— 两者自变量不同。

| valid | n | push 均值 µs | 方差 |
|---:|---:|---:|---:|
| 8  | 80 | 0.88 | 0.209 |
| 16 | 180 | 1.20 | 0.160 |
| 24 | 200 | 1.68 | 0.239 |
| 32 | 260 | 1.96 | 0.260 |
| 40 | 80 | 1.85 | 0.177 |
| 48 | 20 | 2.10 | 0.090 |
| 64 | 140 | 2.71 | 0.276 |

```
push = 0.765 + 0.0303 × valid   (µs)
```

**push 已在 task span 内**（960/960 全部落在所属 GEMM 区间内），
所以 v1 并没有漏掉它；缺的是"把它的 valid 斜率从 nq 斜率里分离出来"。

### 2) 同一 CTA 相邻任务之间的空白

| 版本 | 样本 | 均值 | 中位数 | 0 值占比 |
|---|---:|---:|---:|---:|
| 旧（tile 粒度） | 1829 | 1.69 µs | 2.0 | 0.00% |
| 新（mb-claim） | 1753 | **1.82 µs** | 2.0 | 0.34% |

分阶段看，说明它是**每任务**固定开销，不是阶段切换一次性开销：

| 类型 | n | 均值 |
|---|---:|---:|
| 同阶段相邻任务 | 1682 | 1.84 µs |
| L1→L2 切换 | 71 | 1.41 µs |

两版实现都稳定出现（1.69 / 1.82），确认不是 trace 伪影。

## 重算

```
纯 GEMM（去掉 push）：  398.40 + 13.3203·nq     [µs/块，已×ntile]
push：                  29.07 +  1.1500·valid   [µs/块，已×ntile]
gap：                   1.82 × 38 = 69.2        [µs/块]
------------------------------------------------------------
合计：                  496.7 + 13.32·nq + 1.150·valid
```

（38 = L1 的 18 个 ntile + L2 的 20 个 ntile）

## 权重

```
wb = 496.7 / 14.47 = 34.3
wa = 0（v1 已独立验证：固定项÷ntile 只有 0.84/0.39 µs）
token 系数 = 1
```

## 三个版本的对比

| 口径 | wb |
|---|---:|
| v1：仅 GEMM task span | 29.5 |
| + push 的 valid 斜率 | 29.5（几乎不变）|
| **+ 任务间空白** | **34.3** |

**push 影响极小（+0.04），空白是主因（+4.8）。**
原因很直接：push 每行只加 0.03 µs，而空白是每任务固定 1.8 µs，
再乘 38 个 ntile 就是 69 µs/块，相当于每块固定开销涨了 16%。

## 提醒

1. `wb=34.3` 与之前的 `26`（手工单点）和 `29.5`（v1）差距不小。
   这一轮 A/B 里先跑的是 26 vs 29，**34.3 还需要单独测**。
2. 空白项绑定"每块跑 38 个 ntile"这个事实。若 ntile 数变化，gap 项按比例变。
3. 空白可能有相当部分来自 `_publish_task` 的 mbarrier 往返，
   属可优化项；在它被优化掉之前，把它计入 wb 才是对当前实现的正确描述。
